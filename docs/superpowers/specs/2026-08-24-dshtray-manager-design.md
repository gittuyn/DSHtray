## 1. 背景与目标

DSHtray 是一个独立的 Windows 桌面管理器，用于管理 DeepSeek Harness（DSH）的单实例生命周期，并让用户明确控制 DSH 是否使用代理。

当前使用场景：

- DSH 默认 Web 地址为 `http://127.0.0.1:3080/`。
- DSH 可以从源码仓库通过 `pnpm dsh web` 启动，也可以从打包的 `DSH.exe` 启动。
- 代理地址为 `http://127.0.0.1:7897`。
- 代理只应作用于 DSH 子进程，不应修改 Windows 全局代理。

### 1.1 目标

1. 通过托盘和状态窗口启动、停止、重启 DSH。
2. 同时支持源码启动目标和打包 `DSH.exe` 目标。
3. 提供可持久化的代理开关和代理地址。
4. 用安全的进程归属策略避免误杀未知程序。
5. 让管理器随 Windows 登录启动，但默认不自动启动 DSH。
6. 同时提供绿色版和 Windows 安装器。

### 1.2 非目标

第一版不包含：

- 多个 DSH 实例同时运行。
- 修改 Windows 用户或系统级全局代理。
- 远程控制 API、浏览器管理页面或网络服务端口。
- DSH 账号登录、凭据和 Token 管理。
- DSH 自动更新系统。
- 将管理器注册为 Windows Service。
- 自动接管任意占用 `3080` 的未知进程。

## 3. 用户体验与功能范围

### 3.1 首次启动向导

首次运行管理器时：

1. 扫描常见位置，寻找 DSH 源码仓库和 `DSH.exe`。
2. 展示发现结果以及检测依据，用户确认或手动选择。
3. 创建源码目标和打包目标；缺失的目标允许以后补充。
4. 让用户选择默认目标。
5. 显示代理地址和“首次默认开启”的代理状态。
6. 保存配置并进入主窗口，不启动 DSH。

自动发现只是辅助功能，不能未经用户确认改变启动目标。

### 3.2 托盘菜单

建议菜单结构：

```text
● DSH 运行中
启动 DSH
停止 DSH
重启 DSH
────────────────
✓ 使用代理
当前目标：DSH 源码
打开 DSH 页面
打开管理器窗口
打开日志目录
────────────────
退出管理器
```

状态为 `external` 时，菜单显示“外部 DSH 正在运行”和“接管此 DSH”；在用户确认接管前，不提供危险的停止操作。

### 3.3 状态窗口

主窗口包含：

- 当前状态卡片：状态、目标、服务地址、PID、代理状态、最近错误。
- 操作按钮：启动、停止、重启、打开 DSH 页面。
- 目标选择：源码模式、打包模式、编辑路径、重新扫描。
- 网络设置：代理开关、代理地址、服务端口。
- 管理器设置：开机启动、关闭窗口行为。
- 诊断区域：日志预览、打开日志目录、复制诊断信息、运行自检。

窗口右上角关闭只隐藏窗口，不停止管理器，不停止 DSH。

### 3.4 代理行为

代理开启时，向新启动的 DSH 子进程加入：

```text
HTTP_PROXY=http://127.0.0.1:7897
HTTPS_PROXY=http://127.0.0.1:7897
NODE_USE_ENV_PROXY=1
```

实现必须保留继承的 `NO_PROXY`，不修改 Windows 全局代理。除非后续单独增加需求，管理器不主动设置 `ALL_PROXY`。

代理关闭时，管理器不主动写入或删除代理变量；DSH 继承管理器启动环境的相关变量。这一语义必须在设置页面中有简短说明，避免用户误以为管理器会强制直连。

DSH 运行时切换代理：

1. 用户点击代理开关。
2. 管理器提示“需要重启 DSH，当前会话可能中断”。
3. 用户取消：恢复开关状态，不重启。
4. 用户确认：执行受保护的 DSH 重启。
5. 新进程启动后重新进行健康检查。

### 3.5 DSH 目标

#### 源码目标

默认命令语义：

```text
command: pnpm
arguments: dsh web
workingDirectory: 用户确认的 deepseek-harness 仓库
```

Windows 下应解析 `pnpm` 的实际可执行入口（通常为 `pnpm.cmd`），不能依赖某个固定安装路径。若找不到 `pnpm`，界面应显示 PATH 检查和手动指定命令的入口。

#### 打包目标

```text
executable: 用户确认的 DSH.exe
workingDirectory: DSH.exe 所在目录
arguments: 用户配置的参数（默认为空）
```

两个目标共享服务地址、代理和生命周期逻辑，但保存独立的工作目录、启动命令和参数。

## 4. 技术架构

### 4.1 组件

```text
Tauri Window / Tray UI
          │
          ▼
Rust Application State
          │
 ┌────────┼────────┐
 ▼        ▼        ▼
Config  Lifecycle  Health
         Manager   Checker
          │
 ┌────────┴────────┐
 ▼                 ▼
Source Adapter   Packaged Adapter
          │
          ▼
Windows Process Ownership
          │
          ▼
DSH process tree
```

Rust 后端是状态唯一来源。托盘菜单和窗口不各自维护一份状态，而是订阅同一个生命周期状态流。

### 4.2 生命周期管理器

生命周期管理器负责：

- 校验目标配置。
- 检查是否有已存在的 listener。
- 创建和记录启动尝试。
- 启动目标并捕获根 PID。
- 轮询健康检查直到成功或超时。
- 发出 `starting`、`running`、`stopping`、`failed` 等状态事件。
- 按用户请求执行停止或重启。

默认启动超时时间建议为 90 秒，以覆盖源码模式首次加载和构建产物较慢的情况；该值属于高级设置。

### 4.3 进程归属

#### 管理器启动的 DSH

- 在启动根进程后，将其加入 Windows Job Object。
- 记录 Job Object、根 PID、启动时间和目标 ID。
- 不使用“管理器退出即杀死 Job”的策略，因为产品要求退出管理器不停止 DSH。
- 停止时先请求正常退出；5 秒后仍存活则只对该 Job Object 执行强制清理。

#### 外部 DSH

- 初始只做命令行、路径、PID、父子关系和监听端口的观察。
- 未明确接管前不将其加入强制清理范围。
- 用户确认接管后，管理器再次验证目标路径、命令和进程树；无法建立安全归属时拒绝接管并保持 `external`。
- 接管后的停止仍必须遵守“只处理已确认目标”的边界，不因端口相同而终止未知程序。

### 4.4 健康检查

- 默认请求 `GET http://127.0.0.1:3080/`。
- 检查请求显式绕过代理，确保本地状态不依赖 `7897`。
- 接受 2xx/3xx 作为就绪状态；连接失败、超时和未知端口分别记录原因。
- 高级设置修改端口后，启动参数和健康检查必须使用同一配置快照。

### 4.5 Tauri 命令与事件

命令边界建议保持小而明确：

```text
get_app_state
start_dsh
stop_dsh
restart_dsh
adopt_external_dsh
set_proxy_preference
save_settings
scan_targets
open_dsh_url
open_log_directory
run_self_test
```

后台事件建议包括：

```text
state_changed
log_appended
startup_progress
confirmation_required
notification_requested
```

所有改变状态的命令必须由 Rust 后端校验当前状态，前端不能通过伪造事件改变生命周期。

## 5. 配置与持久化

建议使用独立目录，不复用旧托盘配置：

```text
%LOCALAPPDATA%\DeepSeekHarnessManager\
├─ config.json
└─ logs\
   ├─ manager.log
   └─ dsh.log
```

配置概念模型：

```json
{
  "version": 1,
  "manager": {
    "startOnLogin": true,
    "startDshOnLogin": false,
    "closeToTray": true,
    "confirmRestartOnProxyChange": true
  },
  "activeTarget": "source",
  "targets": {
    "source": {
      "label": "DSH 源码",
      "kind": "source",
      "workingDirectory": "",
      "command": "pnpm",
      "arguments": ["dsh", "web"]
    },
    "packaged": {
      "label": "DSH.exe",
      "kind": "packaged",
      "executable": "",
      "workingDirectory": "",
      "arguments": []
    }
  },
  "service": {
    "host": "127.0.0.1",
    "port": 3080
  },
  "proxy": {
    "enabled": true,
    "url": "http://127.0.0.1:7897"
  }
}
```

第一版只允许服务 `host` 使用 `127.0.0.1` 或 `localhost`；高级设置只开放 `port` 修改，不支持把 DSH 暴露到局域网或任意网卡。

持久化要求：

- 写入临时文件后原子替换正式配置。
- 配置包含版本号，预留迁移机制。
- 解析失败时备份损坏文件，恢复安全默认值并通知用户。
- 不写入 API key、Token 或其他 DSH 凭据。
- 当前 PID、运行状态、Job Object 句柄和错误堆栈不写入持久配置。

## 6. 错误处理与安全边界

必须区分并展示以下错误：

- 目标目录或 `DSH.exe` 不存在。
- `pnpm` 不在 PATH 中。
- 启动命令创建失败。
- `3080` 被未知程序占用。
- DSH 启动超时。
- DSH 进程存在但页面不可访问。
- 代理 URL 格式错误。
- 代理不可用导致 DSH 自身请求失败。
- 配置文件损坏或无权限写入。
- 停止请求超时。
- 已有另一个 DSHtray 实例运行。

安全规则：

1. 不以“端口等于 3080”作为杀进程依据。
2. 不对未知 PID 使用递归强制终止。
3. 只清理管理器创建或用户明确确认接管的目标。
4. 代理只改变 DSH 子进程环境，不修改系统设置。
5. 所有可能中断 DSH 会话的操作都提供明确提示。
6. 安装器默认采用当前用户范围，除非用户明确选择需要管理员权限的安装方式。

## 7. 打包与安装

### 7.1 绿色版

绿色版包含 Tauri 可执行文件及必要资源，解压后直接运行。配置和日志仍写入 `%LOCALAPPDATA%\DeepSeekHarnessManager`，不写入程序目录，以避免权限和升级问题。

### 7.2 安装器

安装器负责：

- 安装程序文件。
- 创建开始菜单或桌面快捷方式（按安装器选项）。
- 提供当前用户开机启动选项。
- 提供卸载入口。
- 卸载时删除管理器自己的启动项；配置和日志默认询问是否保留。

安装器不应自动启动 DSH。管理器首次启动后也不应因安装完成而无提示启动 DSH。

### 8.2 Windows 集成测试

- 正常停止成功时不会强制终止。

- 未知 listener 不被停止。
- 外部目标默认只观察。

### 8.3 手工验收

- 绿色版启动、托盘、设置、退出。
- 安装器安装、升级模拟、卸载。

## 10. 风险与待实现时确认的细节

1. 当前机器上的 `pnpm` 可能是 `.cmd` 入口，源码适配器需要在 Windows 上做实际解析和测试。
2. 外部 DSH 的“接管”不能保证所有进程都能安全纳入同一个 Job Object，因此必须允许管理器拒绝不安全的接管请求。
3. DSH 运行时可能产生比当前根进程更复杂的子进程关系，集成测试需要以实际启动树为准。
4. Tauri 前端框架尚未锁定；第一版优先选择依赖少、适合状态面板的 TypeScript 方案，不因此改变 Rust 后端边界。
5. 代理关闭时继承父环境是已确认行为，设置页必须明确显示“管理器不主动注入代理”，避免把它误解为强制直连。
